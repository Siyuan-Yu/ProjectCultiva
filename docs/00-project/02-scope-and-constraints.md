## 2. 竞品的真实规模（用来校准预期）

两款竞品都是多人团队 + 数年开发，且成本大头是**内容量**（事件文本、功法条目、美术资源），不是系统复杂度。

结论：单人项目不可能在内容量上竞争，只能在**系统精巧度**和**单一体验的锐度**上竞争。因此策略是：

> 系统做深，内容做窄，美术做省。

## 3. 范围控制原则

1. **垂直切片优先**：先做"一个区域、一条修行路线、一套战斗、五个事件"的完整可玩闭环，再横向扩。
2. **一切内容配置化**：任何"以后要加很多个"的东西（功法、丹药、事件、妖兽）必须从第一天就是配置表驱动。
3. **每个系统必须先有单页设计文档**才允许写代码，文档写不清楚说明设计没想清楚。
4. **可砍性标注**：每个系统在设计文档里标注优先级 P0/P1/P2，P2 默认不做。
5. **不追求引擎最佳实践的完备性**，追求能跑、能改、能交接。

## 4. 技术约束（已定）

- Unity 版本一旦选定不随意升级，理由记录在 ADR。
- 不引入需要付费或授权不明的第三方插件，除非记录在 ADR 中。
- 所有游戏数值不写死在代码里。
- 存档格式从第一版就要考虑版本迁移。
